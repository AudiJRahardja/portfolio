Spam & Scam-Type Classifier

A two-stage filter for English and Indonesian SMS, email and chat: is a message unwanted, and if so, is it promo, a scam, phishing or gambling?

Nov 2026 – now

Earlier related work: Fake Review Detection (NLP course) (opens in a new tab)

The problem

Scam, phishing and online-gambling ("judol") messages reach people in English and Indonesian, over SMS, email and chat. Public spam datasets are mostly English and usually only say "spam", not what kind. I want a filter that also says what kind of unwanted message it is and how risky it is.

My part

Everything so far: the source registry, 11 dataset loaders, the anonymiser, the labelling guide, the labelling tool and the hand labels.

How it works

7 stages, 3 still planned (dashed). Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 07

Collect sources

Done
Input

12 sources listed in one registry, each with its licence, citation and label map

Operation

A download script fetches each one from its URL, Kaggle, Hugging Face or Mendeley

Output

Raw files in data/raw/<source>/, never edited by hand

  • Licences and citations were checked against each source's own page on 21 Nov 2026.
  • English: UCI SMS, Mendeley smishing, a phishing-email bundle (Enron, Nazario, Nigerian Fraud and more), Telegram and SmishTank.
  • Indonesian: two SMS sets, online-gambling comments and posts, and translated emails. The 12th source is my own collection, still a template.

Flow: sources.yaml >> download_data >> data/raw/<source>

Stage 02 of 07

Unify labels

Done
Input

Raw files, each with its own labels ("spam", "Smishing", 0 / 1…)

Operation

One loader per source maps its labels onto one shared set and tags how the rows may be used

Output

One table of 138,798 messages with text, label, language, channel and role

  • Shared labels: ham, promo, scam, phishing and gambling. Spam with no type stays "untyped" and only trains the first stage.
  • Every source gets a role: train, eval-only, fresh test ("spam from after training") or translated slice, so held-out sets never leak into training.
  • Row counts are checked against the counts recorded for each source. Label fixes go in a separate file; raw data stays untouched.

Flow: load_source >> map_labels >> tag_role >> messages.parquet

Stage 03 of 07

Anonymise

Done
Input

Messages from real phones, collected with consent

Operation

Mask e-mails, phone and account numbers, names and the personal parts of links

Output

Text with <PHONE>, <EMAIL>, <ACCOUNT>, <NAME> and <ID> tokens, plus rows flagged for a human check

  • Keeps the useful spam signals: link domains, money amounts and short codes.
  • Over-masks on purpose: a wrong <ACCOUNT> costs a little signal, a leaked number costs someone's privacy.
  • Covered by unit tests.

Flow: mask_email >> mask_numbers >> mask_names >> mask_url >> flag_residual

Stage 04 of 07

Hand-label

Ongoing
Input

Spam rows that have no type yet

Operation

Give each one a type in a Streamlit tool, following a written labelling guide

Output

300 messages so far: 283 labelled, 17 skipped as unclear

  • The guide asks five questions in a fixed order and stops at the first "yes". Rules settle tricky cases: a prize with a link is phishing, without a link it is a scam.
  • Review mode and whole-word label suggestions make it faster.
  • So far: 130 scam, 107 promo, 27 phishing, 14 gambling and 5 that turned out to be normal.

Flow: sample_untyped >> label_tool >> hand_labels.csv

Stage 05 of 07

Clean & dedupe

Planned
Input

The unified table

Operation

Check each message's language and drop near-duplicate messages

Output

Not known yet

Stage 06 of 07

Train & compare

Planned
Input

Train / validation / test splits by message id

Operation

Stage A: normal vs unwanted. Stage B: promo, scam, phishing or gambling. Four models on the same splits

Output

Scores per language and channel, each next to a baseline

  • Baseline: TF-IDF bag-of-words + Naive Bayes, the simplest model.
  • Logistic Regression and LightGBM on word and character n-grams plus message metadata, and a fine-tuned multilingual transformer.
  • Also tested on the fresh SmishTank spam and the translated slice, which are never trained on.

Flow: make_splits >> tfidf >> fit(nb, logreg, lgbm, transformer) >> compare

Stage 07 of 07

Explain & demo

Planned
Input

A trained model and a new message

Operation

Show which words pushed the decision and give a harm risk score

Output

A Streamlit demo: paste a message, see its type, risk and why

  • Scam, phishing and gambling count as harmful; promo is annoying, not dangerous.
  • The filter's strictness will be adjustable.

Flow: predict >> explain(shap, lime) >> risk_score >> streamlit

Results so far

No model is trained yet, so there are no accuracy numbers. They will appear here next to a baseline.

  • 138,798 messages in one table About 139 thousand messages to learn from. 11 datasets; 134,900 of them may be used for training Source: reports/metrics/dataset_counts.csv
  • 23,362 Indonesian messages About 1 in 6 messages is Indonesian; the other 115,436 are English. Language as declared by each source Source: reports/metrics/dataset_counts.csv
  • 1,062 fresh spam messages held out Newer spam the models never see in training, to check they still work on new scams. SmishTank, used only as a test set Source: reports/metrics/dataset_counts.csv
  • 300 messages labelled by hand 283 got a type; 17 were too unclear and skipped. Untyped spam, labelled with the written guide Source: data/hand_labels.csv

What I learned

  • Public datasets label spam very differently. Mapping them all onto one shared label set, and keeping "untyped" spam out of the type classifier, mattered more than any model choice so far.
  • Scam vs phishing vs promo is a judgement call. A written decision order with rules for tricky cases made my hand labels consistent.
  • Privacy comes before the data: messages from real phones are masked before they are stored, and the rules over-mask on purpose.

What's next
