LifeBase

A local-first personal "second brain" that syncs an Android phone and a browser through my own Supabase project. Only to-dos exist so far.

Oct 2026 – now

The problem

I want one personal app for my to-dos, schedule, routines, notes and gym log that works on my Android phone and in the browser on my PC. It should open instantly and work offline, and the data should live in my own database, not in someone else's app.

My part

Architecture and overall idea. Early stage, and I'm learning the stack as I go.

Solo · Personal learning project

  • Expo
  • React Native
  • TypeScript
  • Supabase
  • rrule (repeating events and routines) (planned)

How it works

7 stages, 1 still planned (dashed). Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 07

Sign in

Done
Input

My email and password, on the phone or in the browser

Operation

Sign in once with Supabase and keep the session on the device

Output

A session that still works offline

  • After creating my one account, new sign-ups are turned off, so nobody else can join the project.
  • Local data is wiped only on sign-out or when a different user signs in.

Flow: sign-in >> session >> AsyncStorage

Stage 02 of 07

Save locally

Done
Input

An edit on any screen, such as adding or ticking off a task

Operation

Write the row and an "outbox" entry for it in one saved update, so neither can be lost without the other

Output

The change on screen at once, plus a queued change waiting to sync

  • Screens never talk to the server; they read through hooks and write through repositories.
  • Row ids are made on the device, so new rows work offline.
  • The local store sits behind an interface so it can be swapped for SQLite later.

Flow: useRows >> createRepository >> localStore + outbox

Stage 03 of 07

To-dos

Done
Input

Tasks and task lists

Operation

Show tasks in Inbox, Today, Upcoming, All or a custom list, with subtasks, priorities and due dates

Output

The one module built so far, on Android and web from one codebase

  • A due time is stored as local wall time, so "5 pm" stays 5 pm.
  • Overdue and due-date labels, sorting and new-task defaults are small pure functions with unit tests.

Flow: ViewPicker >> tasksForView >> sortTasks >> TaskRow

Stage 04 of 07

Sync engine

Done
Input

The outbox and the time of the last pull for each table

Operation

Push queued rows (parents before children), then pull rows changed on the server since the last pull, minus a 10-second overlap

Output

Phone and browser hold the same data; the last write to reach the server wins per row

  • Runs on app start, on reconnect, when the app comes back to the front, 1.5 s after an edit and every 60 s.
  • Deletes are soft (deleted_at) so they sync like edits. An edit made during a push is not lost.
  • 15 unit tests against a fake server cover offline edits, crashes mid-push, conflicts, paging and the overlap window.

Flow: startSyncLoop >> requestSync >> syncOnce >> push >> pull

Stage 05 of 07

Own database

Done
Input

Rows pushed from my devices

Operation

Store them with row-level security, and let a server trigger set every updated_at

Output

My data in my own free Supabase project, readable only by my user

  • Because the server sets the timestamps, a wrong clock on a device does not break sync.
  • The app only holds the public key; the service key is never in the client.
  • No unique rules besides the id, because two offline devices could break them and block sync.

Flow: supabaseRemote.upsert >> schema.sql (RLS) >> pullSince

Stage 06 of 07

Backup

Done
Input

Operation

Flow: buildBackup >> backupFileName >> saveTextFile

Results so far

This is an early learning project with no users besides me, so there are no usage numbers.

  • 25 unit tests 15 for the sync engine and 10 for the to-do logic. Jest; run with npm test Source: src/sync/engine.test.ts, src/features/todos/logic.test.ts
  • 10 database tables with row-level security Every table only lets my own user read or change its rows. Tables for all planned modules; only the to-do tables are used so far Source: supabase/schema.sql
  • 1 of 5 modules built To-dos work; schedule, routines, notes and the gym tracker are still to come. Early stage learning project Source: README.md

What I learned

  • Letting the server set every timestamp means device clocks never matter for sync.
  • Unique rules that look harmless can block sync forever when two offline devices both write; duplicates are removed when reading instead.
  • Writing the sync engine against a fake server made it possible to test offline edits, crashes and conflicts without a phone.

What's next
