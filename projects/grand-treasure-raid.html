The Grand Treasure Raid

A Discord-login puzzle event site for BINUS Game Development Club, with checkpoints that unlock on a schedule and a live leaderboard.

Oct 2026

Live demo (opens in a new tab)Code (opens in a new tab)

The problem

BINUS Game Development Club wanted a recurring online puzzle event for its Discord community. It had to be fair, hard to cheat and easy to run: only club members should play, nobody should be able to read the answers, and the organiser should not need an admin screen or a bot.

My part

Everything: design, build, security hardening and deployment.

How it works

7 stages. Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 07

Author puzzles

Done
Input

A puzzle designed by the organiser, saved as JSON in a git-ignored private/ folder

Operation

A checker solves the puzzle and makes sure it has exactly one solution, then the organiser inserts it with copy-paste SQL

Output

An event with checkpoints, each with an unlock time and a stored solution

  • Answers are compared by exact equality, so a puzzle with two solutions would mark a correct solve as wrong. The checker catches that for sudoku, queens and crossmath.
  • make-crossmath turns a layout into a finished crossmath with one solution. Riddles have no checker, so every accepted spelling is listed.
  • Every time is written with the +07 offset; without it a checkpoint would unlock 7 hours late.

Flow: check-puzzle >> make-crossmath >> adding-puzzles.md SQL >> puzzles + puzzle_solutions

Stage 02 of 07

Sign in

Done
Input

A player taps "Login with Discord", often from inside the Discord app

Operation

Exchange the login code with cookie writes held back, then save only the access and refresh tokens

Output

A login cookie that does not contain Discord's token

  • Discord's token is used once on the server for the membership check and is never stored in the cookie.
  • After login the player returns to the page they wanted. Off-site redirects such as //evil.example fall back to /puzzles.
  • Logged-out visitors are sent from /puzzles, /leaderboard and /verify to the login page.

Flow: DiscordLoginButton >> auth/callback >> exchangeCodeForSession >> setSession >> safeNext

Stage 03 of 07

Check membership

Done
Input

The fresh Discord token and the Supabase user

Operation

Ask Discord whether this account is in the BGDC server, after checking it is the account linked to the login

Output

A membership check stored in guild_members, valid for 21 days

  • Uses the standard guilds.members.read login scope: no bot and no privileged intents.
  • Discord errors, rate limits and timeouts never count as "not a member"; the player sees "Couldn't check, try again".
  • Only the server, with the secret key, can record a check, and the database refuses a Discord id that is not the player's own.

Flow: verifyGuildMembership >> discordGet(/users/@me) >> discordGet(guild member) >> record_guild_check

Stage 04 of 07

Unlock checkpoints

Done
Input

The event's checkpoints and their unlock times

Operation

List open checkpoints and show locked ones with a countdown, using the database clock

Output

Checkpoint cards: open, solved, or "opens ..." in WIB

  • Players can read a puzzle's title and type only after it unlocks; the puzzle content itself is never readable directly.
  • Countdowns use the server time, so changing the phone clock does not open anything early.

Flow: checkpoint_schedule >> server_now >> Countdown

Stage 05 of 07

Play puzzle

Done
Input

A player presses Start on an open checkpoint

Operation

The database hands out the puzzle content and starts that player's timer; the matching game component renders it

Output

A playable riddle, sudoku, queens or crossmath board

  • Four puzzle types, picked from one registry; queens and crossmath use drag and drop, sudoku has notes.
  • A half-filled grid survives a page reload, and the timer keeps running.
  • Each game has its own guide on the Start screen and a "How to play" dialog.

Flow: PuzzlePlayer >> start_puzzle >> GAMES[type] >> useSavedState

Stage 06 of 07

Check answer

Done
Input

The player's answer as JSON

Operation

Check membership, that the puzzle is open, the cooldown and the answer, all inside one database function

Output

Correct with the solve time, wrong with a 60-second wait, or a cooldown message

  • One wrong answer per minute, counted across all checkpoints. A row lock stops double-clicks from racing.
  • Riddles ignore case and extra spaces; grid puzzles must match the stored solution exactly.
  • Solve time is counted from Start to the correct answer on the database clock. Every attempt is logged.

Flow: SubmitButton >> submit_answer >> is_guild_member >> submissions + progress

Stage 07 of 07

Leaderboard

Done
Input

Every member's solved checkpoints

Operation

Sum the points (1 per puzzle by default), then the lowest total solve time, then whoever finished earlier

Output

A ranked table, with the viewer's own row marked "You"

  • Only verified members are listed and ranked, so a faster non-member cannot push members down.
  • Seeing the leaderboard needs a current membership check, like playing.

Flow: leaderboard view >> LeaderboardTable

Results so far

There are no player or usage numbers in the repository yet.

  • 4 puzzle types Riddle, sudoku, queens and crossmath, each with its own game screen. Built for the event; no player numbers recorded Source: README.md
  • 0 review findings that expose answers The security review found no way for a player to see solutions, see other players' answers, or play without being a member. Tested by running the real SQL in a local Postgres engine (PGlite) as members, non-members and logged-out visitors Source: docs/security-review.md
  • 2 hardening migrations Two database updates: size limits on names and answers, then the BGDC members-only rule. 002_hardening.sql and 003_guild_membership.sql, run after schema.sql Source: README.md
  • 60 s wait after a wrong answer Guessing is slow: one wrong try per minute, across all checkpoints. Enforced in the database, not the browser Source: supabase/migrations/003_guild_membership.sql

What I learned

  • Exact-match answer checking only works if each puzzle has one solution, so a uniqueness checker became part of writing every puzzle.
  • A failed Discord check is not the same as "not a member". Treating errors as unknown keeps real members from being locked out when Discord is slow.
  • Putting every rule in the database (row-level security and two functions) means the site only needs the public key, and a modified browser cannot skip the checks.

What's next

  • Replace user_id in the leaderboard view with an is_me flag, so members no longer see each other's ids (security review, finding 1).
  • Add security headers such as X-Frame-Options and a Content-Security-Policy in next.config.ts (security review, finding 10).
