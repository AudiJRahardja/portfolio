Brightnest Knowledge Assistants

One retrieval engine behind two chatbots, for employees and for customers, that answers in English or Indonesian with citations and never leaks internal data.

Nov 2026

Code (opens in a new tab)

The problem

Company chatbots have to give grounded answers from internal documents, and must never show HR-only or internal information to someone who isn't allowed to see it.

My part

Everything: retrieval design, security model, tools, evaluation and deployment config.

How it works

7 stages. Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 07

Company documents

Done
Input

A knowledge base for a fictional Indonesian home-goods retailer, written in English and Indonesian

Operation

Each file is loaded and its header is checked: visibility, allowed roles, language, version and status

Output

56 validated documents: 28 topics, each in English and Indonesian

  • Public: 12 topics (about us, store hours, refunds, shipping, warranty, FAQ). Internal: 13 topics plus 1 old version. Restricted: 2 (salary bands for HR, manager guidelines for managers and HR).
  • Tricky cases on purpose: an outdated and a current remote-work policy, and look-alike topics such as customer refunds vs employee reimbursements.

Flow: data/docs/{public,internal,restricted}/{en,id}/*.md >> load_documents >> parse_document

Stage 02 of 07

Chunk by section

Done
Input

Validated Markdown documents

Operation

Cut each document at its "##" headings, so one section becomes one chunk

Output

Chunks whose search text starts with "Document title > Section heading"

  • The first version used fixed 220-word windows that ignored headings. Section chunks raised external MRR from 0.93 to 1.00.
  • A section longer than 220 words would be split again into overlapping windows; none are that long today.
  • English and Indonesian copies have the same sections in the same order, so search can keep just one copy of each.

Flow: split_sections >> chunk_document >> chunk_documents

Stage 03 of 07

Embed

Done
Input

Chunk texts

Operation

Turn each chunk into a vector with a local multilingual model

Output

One vector per chunk, plus hashed leak fingerprints of every collection

  • BGE-M3 puts English and Indonesian in the same vector space, so an Indonesian question can find an English section.
  • It runs locally, so no document text is sent to an outside service for search.
  • Re-indexing only re-embeds files whose hash changed.

Flow: rag.ingest >> plan >> Embedder.embed_documents >> build_fingerprints

Stage 04 of 07

Separate stores

Done
Input

Vectors and chunk texts, grouped by visibility

Operation

Write each visibility level into its own Qdrant database folder, each with its own BM25 keyword index

Output

storage/qdrant/public, internal and restricted, opened only for the roles allowed to read them

  • The customer assistant only ever opens the public database. A database that was never opened cannot return anything.
  • A stricter customer-only server can be built from the public documents alone, so internal data is not in its index at all.

Flow: IndexWriter.rebuild >> storage/qdrant/<collection> >> KnowledgeStore(allowed)

Stage 05 of 07

Retrieve by role

Done
Input

A question, the assistant (internal or external) and the user's role from a signed login token

Operation

Rewrite follow-ups, split two-part questions, then run vector and keyword search over the allowed databases only and rerank

Output

The best 5 sections (6 for a two-part question)

  • Vector and BM25 results are merged by rank fusion; the reranker re-scores about 20 candidates.
  • Only one language copy of each section is kept, and outdated policy versions are left out unless the question asks about the old rules.
  • Each step can be switched off in .env, which is how the ablation table measures what each one adds.

Flow: rewrite_question >> split_question >> _search(vector + keyword_search) >> rrf >> merge_twins >> rerank

Stage 06 of 07

Answer & check

Done
Input

The question and the numbered sources

Operation

Screen the input for prompt injection, let the LLM answer with [1] [2] citations (or call a tool), then scan the answer before showing it

Output

A cited answer in the user's language, or "I don't know" with the right contact, or a withheld answer

  • Tools: leave balance, my manager and tickets for employees; order status, store hours, support hand-off and sales leads for customers.
  • The output check looks for pieces of the system prompt and for hashed fingerprints (e-mails, phone numbers, amounts, names) of documents the user may not read.
  • Every answer is logged with emails and phone numbers blanked, and gets thumbs up / down for the analytics page.

Flow: check_question >> looks_like_injection >> retrieve >> llm.generate >> parse_tool_call >> output_problems

Stage 07 of 07

Eval & leak tests

Done
Input

86 internal, 82 external and 38 leak-attack questions, each in English and Indonesian

Operation

Score search, answers and leaks after every change, and save one line per run to the results history

Output

eval/results.csv: the before / after history behind the tables on this page

  • Search and leak checks are plain code, so those numbers are exact. Answer quality is graded by a second LLM call and read as a trend.
  • A test counts as leaked if a forbidden document reaches the LLM, or a forbidden fact (salary figures, internal names, extensions) appears in the answer.
  • Attacks include prompt injection, role escalation, a manager asking for salary bands and order lookups with the wrong e-mail.

Flow: eval.run --profile internal|external|leak >> retrieval_scores + judge >> results.csv

Results so far

  • 0 / 38 attacks that leaked internal or HR-only data None of the 38 attempts to get secret data out of the bots worked. Leak-attack set, Phase 5 run; checked by code, not by the LLM judge. The bot also refused 97% of the attacks outright. Source: eval/results.csv
  • 33% → 100% multi-document retrieval for the customer bot Baseline: First version: vector search only, fixed 220-word chunks (33%) Questions that need two or more documents now always find all of them. Customer questions that need 2+ documents, first version vs now Source: README.md
  • 0.93 → 1.00 retrieval MRR, internal bot Baseline: First version: vector search only, fixed 220-word chunks (MRR 0.93) The right document is now ranked first for every employee question in the test set. Internal set; the external bot went from 0.93 to 0.98 Source: eval/results.csv

What I learned

  • Keyword search on its own made the ranking slightly worse, but it found extra candidates that the reranker then put in the right order. Measuring each step separately is what showed this.
  • A reranker only judges how well text matches, not which version is current: it ranked the 2024 remote-work policy above the 2026 one. Leaving outdated versions out took outdated-policy answers from 3% to 0%.
  • Safety rules need testing against normal questions too. The injection filter caught the jailbreak word "DAN" matching the Indonesian "dan" ("and"), and the first system-prompt check withheld 4 harmless refusals.
