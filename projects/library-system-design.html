Library Booking System: design & docs

System design for a library reservation and loan system: use-case, class, activity and sequence diagrams, plus architecture and user-flow documentation.

Apr 2026

The problem

A library needs members to find and reserve books, see when a loan is late and pay the fine, while an admin keeps the catalogue and member list up to date. Our group had to design this system before building it. My part was turning those requirements into diagrams the build could follow.

My part

Made all the UML, activity and sequence diagrams, and co-wrote the architecture and user-flow documentation with a teammate (in the SRS document, submitted through BinusMaya).

How it works

6 stages. Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 06

Register & log in

Done
Input

A visitor opens the site and types their details or their username and password

Operation

The system checks the data (ID on sign-up, password on log-in) and shows an error if it is not valid

Output

A saved account, or the member or admin dashboard after log-in

  • Use case: Register includes "Verify ID"; Login includes "Verify Password" and is extended by "Display Login Error".
  • Both activity flows loop back to the form on a "Valid? no" branch.
  • One log-in serves both roles: the User class is the parent of Customer and Admin.

Flow: register() >> verify ID >> save account >> login() >> verify password >> dashboard

Stage 02 of 06

Search books

Done
Input

Keywords typed into the search page

Operation

The system searches the book table by keyword

Output

A list of matching books, or a "Sorry, no books found." message

  • The sequence diagram splits the work across App, System and Database.
  • An alt block covers both outcomes: results found and not found.

Flow: open search >> send keywords >> search_books() >> list or "not found"

Stage 03 of 06

Reserve a book

Done
Input

A member clicks "Reserve" on a book

Operation

The system checks the book's status; if it is available it marks it "Reserved" and saves a reservation record

Output

"Book Reserved Successfully!" or "Sorry, this book is unavailable."

  • Book status is one of "Available", "Reserved" or "On Loan" (class diagram).
  • Use case: Book/Reserve includes "Verify Book Availability" and is extended by "Display Error Booking".
  • Each reservation is a Transaction with an id, a type and a date.

Flow: reserve_books() >> query book status >> update_status("Reserved") >> save reservation

Stage 04 of 06

Check late status

Done
Input

A member opens the "Borrowing Status" menu

Operation

The system fetches the member's loans and due dates and works out how late each one is

Output

The late status shown to the member

  • Rule written in the diagram notes: late duration = current date minus due date.
  • The Member class keeps a late_status and an account balance.

Flow: cek_late_status() >> fetch borrowing data >> calculate late duration >> show status

Stage 05 of 06

Pay late fees

Done
Input

A member clicks "Pay Late Fees"

Operation

The system calculates the fee, the member confirms, and the transaction is processed and marked "Paid"

Output

A receipt for the payment

  • Fee rule in the diagram notes: late duration times a daily fee rate.
  • Use case: Pay Late Fees includes Check Late Status, so the fee is always worked out first.
  • Penalty.calculate_fine() and Transaction.print_receipt() carry this in the class diagram.

Flow: pay_late_fees() >> calculate_fine() >> confirm payment >> process() >> print_receipt()

Stage 06 of 06

Admin tools

Done
Input

An admin opens Manage Books or Manage Members

Operation

Add, edit, view or delete a book after the data is checked; or open a member's history

Output

An updated catalogue with a confirmation, or a member's borrowing history and status

  • Manage Books is extended by Add, Edit, View and Delete Books.
  • Manage Members is extended by View Member History.

Flow: add_book() / edit_book() / delete_book() >> verify data >> update database | manage_member() >> view_member_history()

  • 7 classes in the data model The data the system keeps: users, books, members, loans and fines. User, Customer, Admin, Book, Member, Transaction, Penalty Source: Class Diagram 14.png

What I learned

  • Each flow is drawn twice: the activity diagram shows the decisions (Valid?, Find?, Available?), and the sequence diagram shows which part (App, System or Database) does each step.
  • The late-fee rule had to agree in three places: the use-case link (Pay Late Fees includes Check Late Status), Penalty.calculate_fine() in the class diagram, and the notes in two sequence diagrams.
  • The course used the project to walk through the SDLC and a GitHub workflow.
