RFID Attendance System

Class attendance with RFID cards on an ESP32 and a Wi-Fi dashboard, with a working Wokwi simulation.

Nov 2026 – now

Live demo (opens in a new tab)Code (opens in a new tab)

The problem

Students tap an RFID card when they arrive instead of signing a list. The reader marks them present once per day, on time or late, and the lecturer sees who came on a web dashboard.

My part

Pipeline and idea.

How it works

6 stages. Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 06

Tap card

Ongoing
Input

An RFID card held to the MFRC522 reader

Operation

The ESP32 reads the card's ID over SPI and turns it into a text UID like "01020304"

Output

The UID plus the current date and time

  • Runs in a Wokwi simulation; the README says it is not set up for a real module yet.
  • On start-up the board joins Wi-Fi and syncs the clock to UTC+7 (WIB) from an NTP server.
  • If Wi-Fi fails it keeps working in offline mode.

Flow: connectWiFi >> syncTime >> PICC_ReadCardSerial >> uid

Stage 02 of 06

Check the card

Ongoing
Input

The UID and today's date

Operation

Look the UID up in a small student table on the ESP32 and check whether it was already used today

Output

One of four results: OK, already recorded, unknown card, or error

  • The local table holds two test students for now.
  • A second tap on the same day is caught as a duplicate.

Flow: checkLocally >> RES_OK | RES_DUPLICATE | RES_UNKNOWN | RES_ERROR

Stage 03 of 06

LCD & buzzer

Ongoing
Input

The check result and the student's name

Operation

Show a message on the screen and play a beep pattern for that result

Output

e.g. the name and "Attendance OK" with one short high beep

  • Duplicate: two medium beeps. Unknown card: one long low buzz. Error: three fast beeps.
  • The screen goes back to "Scan your card" after 1.8 seconds.

Flow: showTimed >> beepSuccess | beepDuplicate | beepUnknown | beepError >> showIdle

Stage 04 of 06

Send over Wi-Fi

Ongoing
Input

The UID, device name, date and time

Operation

POST them as JSON to the backend with an API key, then read back the status and name

Output

A reply like {"status":"ok","name":"..."}

  • Written in the sketch but switched off (USE_SERVER is false) and the server URL is still a placeholder.
  • Uses setInsecure() for testing only; the code notes a CA certificate is needed for real use.

Flow: checkWithServer >> POST /api/tap >> deserializeJson >> Result

Stage 05 of 06

Record attendance

Ongoing
Input

A tap sent to POST /api/tap

Operation

Find the student by card UID, block a second record on the same day, and mark the tap late after 07:30

Output

A row in the attendance table, or a row in the unknown table for an unregistered card

  • Four tables: students, cards, attendance and unknown. A student may own more than one card.
  • The database itself blocks a second record per student per day (a UNIQUE rule on student and date).
  • On a separate dashboard branch, not merged yet.

Flow: receive_tap >> lookup card >> duplicate check >> on_time | late >> INSERT attendance

Stage 06 of 06

Dashboard

Ongoing
Input

The attendance, student and unknown-card tables

Operation

Show the day's numbers, a daily trend, searchable records and unknown cards

Output

An overview page plus a CSV export of the records

  • Overview: total students, present, late, absent and attendance rate.
  • Tested so far with generated fake data, not real taps.

Flow: /api/dashboard >> /api/trends >> /api/attendance >> /api/export.csv

Results so far

Still in progress and only simulated, so there are no test results yet. The firmware and the dashboard are not connected yet.

  • 4 tap outcomes handled Every tap ends in one clear answer: present, already counted, unknown card, or error. Each has its own LCD message and beep pattern Source: sketch.ino
  • 07:30 default late cut-off Taps after half past seven count as late. Set by LATE_AFTER; can be changed Source: attendance_rfid_dashboard/.env.example (feature/attendance-dashboard branch)
  • 1 record per student per day Tapping twice never counts you twice. Checked on the ESP32 and enforced by the database Source: sql/Schema.sql

What I learned

  • The ESP32 keeps a small local student table so taps still work when the server or Wi-Fi is down.
  • Duplicate taps are checked twice: on the board and by a UNIQUE rule in the database, so a retry cannot create a second record.
  • The dashboard counts "absent" as all students minus those present, which assumes everyone has class that day. A schedule table is still missing.

What's next

  • Turn on USE_SERVER and point the ESP32 at the FastAPI /api/tap endpoint.
  • Merge the dashboard branch and test it with real taps instead of fake data.
  • Replace setInsecure() with a CA certificate.
  • Add a class schedule table and a way to assign unknown cards to students.
  • Set the project up for a real ESP32 and RFID module.
