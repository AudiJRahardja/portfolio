Voice Chess

Play chess against Stockfish by voice, with a fine-tuned Whisper and a wake-word model that run entirely in the browser.

Sep – Oct 2026

Live demo (opens in a new tab)Code (opens in a new tab)Model (opens in a new tab)

The problem

Speech recognisers that work out of the box handle chess notation badly ("rook to e4", "knight d2"), and browser speech APIs send your audio to a server. I wanted hands-free, accessible chess that runs on-device.

My part

Everything: data generation, model training, evaluation and the web app.

How it works

7 stages. Pick a stage to see what goes in, what happens and what comes out. Arrow keys move between stages.

Stage 01 of 07

Generate commands

Done
Input

Random legal chess games played by a script

Operation

Phrase each move, question, yes / no answer, correction and wake phrase the way players say them, then check every label with the app's own parser and matcher

Output

40,000 command lines for training, plus a separate 1,500-line test list

  • There is no public dataset of spoken chess commands, so the text had to be generated.
  • A label the app would misread is thrown out, so the model is never taught a phrase the app cannot use.
  • Round 2 added 8,000 rank-3 commands written to be voiced as "tree" or "tri" (ml/text/accent.mjs).

Flow: generateCommands >> interpretTranscript check >> commands.jsonl

Stage 02 of 07

Make the audio

Done
Input

The command lines, plus slices of public speech corpora

Operation

Voice each line with Piper's 904-speaker voice, mix in real speech, and add room echo, noise and cheap-microphone effects

Output

About 40,000 synthetic clips, split by speaker into train / validation / test

  • Real speech where it overlaps: LibriSpeech (4.3k utterances), Speech Commands (about 7k clips) and CMU AN4 (about 1.1k utterances).
  • Three other Piper voices (alan, amy, ryan) are never trained on: the "unseen voice" test sets.
  • Room echo and noise come from OpenSLR 28.

Flow: voicechess.download >> voicechess.synth >> augment >> manifest.jsonl

Stage 03 of 07

Fine-tune Whisper

Done
Input

The mixed training clips

Operation

Fine-tune Whisper-base (74M parameters), sampling each source by weight so 40k synthetic clips do not drown out the real ones

Output

A chess-command recogniser, published on Hugging Face

  • 4,000 steps in fp16 on an RTX 2060, about 45 minutes.
  • Ordinary English stays fine: LibriSpeech word error rate is 7.5% after fine-tuning, 8.2% before.
  • Round 2 retrained with the rank-3 "tree" clips after error analysis on real speech.

Flow: train_whisper --name base-tree --steps 4000 >> runs/base-tree/final

Stage 04 of 07

Train wake word

Done
Input

Synthetic "make move" / "hey chess" clips and near-miss phrases like "nice move" or "hey jess"

Operation

Train a small depthwise-separable CNN from scratch that computes its own log-mel spectrogram inside the network

Output

A 21k-parameter wake-word model, 0.7 MB as ONNX

  • 3,000 training steps, about 13 minutes.
  • At the shipped threshold (0.8) it misses about 1% of wake phrases from held-out speakers and 15% from unseen voices.
  • About 2 false triggers per hour of LibriSpeech. A false trigger only makes the app listen; nothing plays without a yes.

Flow: wakeword data >> wakeword train >> wakeword eval >> wakeword export

Stage 05 of 07

Score by behaviour

Done
Input

Transcripts from every system on every test set, including 150 real commands I recorded

Operation

Run each transcript through the same respond() the app uses and check whether the app would do the right thing

Output

ml/results/summary.json: commands understood, wrong moves and word error rate per system and test set

  • Compared against Chrome Web Speech (the v1 engine) on the same audio, and stock Whisper tiny, base and small.
  • Round 1 vs Chrome: 13 commands right that Chrome got wrong, 2 the other way (exact McNemar p = 0.007).
  • Also scores the exact 8-bit files the browser loads, not only the full-precision model.

Flow: transcribe >> hyps/*.jsonl >> score.mjs (respond) >> summary.json

Stage 06 of 07

Run in browser

Done
Input

Microphone audio in the browser

Operation

Capture 16 kHz audio, find the start and end of speech, listen for the wake word, then transcribe with the 8-bit Whisper in a worker

Output

A transcript about 1 to 1.5 s after the command, with no audio leaving the device

  • The 8-bit model is a 98 MB download, cached after the first visit.
  • The page is cross-origin isolated so WebAssembly can use several threads.
  • Falls back to the browser's own recogniser if the on-device model cannot run.

Flow: capture-worklet >> Endpointer >> wake model >> speech.worker (Whisper q8) >> transcript

Stage 07 of 07

Parse & confirm

Done
Input

A transcript, typed or spoken

Operation

Turn the words into a candidate move, match it against the legal moves, read it back and wait for "yes"

Output

A legal move played against Stockfish, or a "which one?" question, or a clear "not understood"

  • The matcher only ever returns a real legal move, so the app cannot invent one.
  • Questions like "where is my queen" are checked before moves, so "what's on e4" is never played as e4.
  • Nothing spoken is played without a yes, and "no, knight d2" corrects in one breath.

Flow: parseTranscript >> matchMove >> interpretAlternatives >> respond >> confirm >> Stockfish

Results so far

  • 96.0% real spoken commands understood, shipped in-browser model Baseline: Chrome Web Speech API (v1): 88.7% Gets about 24 of 25 spoken commands right, against about 22 of 25 for Chrome. 150 real commands, one speaker; scored by what the app does Source: ml/results/summary.json
  • 5.4% word error rate on the same real speech Baseline: Chrome Web Speech API: 26.2% About 1 word in 20 is wrong, against about 1 in 4 for Chrome. Shipped 8-bit model, greedy decoding Source: ml/results/summary.json
  • 99.3% commands understood, held-out synthetic speakers Baseline: Stock Whisper-base: 71.4% Fine-tuning took the same model size from about 7 in 10 to almost all commands. Synthetic voices never trained on Source: ml/results/summary.json
  • ~1.9 / hour wake-word false triggers on ordinary speech About twice an hour it wakes up by mistake, and it then still waits for a yes. Threshold 0.8; misses 1.1% of held-out speakers' wake phrases Source: ml/results/wakeword-eval.json

Caveat: The real-speech test set is a single speaker, so treat it as a strong signal, not a general claim.

What I learned

  • With no public dataset, the labels had to be trustworthy by construction: every generated command is checked by the app's own parser and matcher before it becomes training data.
  • Scoring by what the app actually does (play, ask, or refuse) told me more than word error rate alone, and the yes / no confirmation is the backstop for the wrong moves that remain.
  • Error analysis beat guessing: every round-1 error on real speech involved rank 3 heard as "tree", so round 2 added 8,000 targeted clips. The gain on the real set is within noise; the held-out "tree" set is the real evidence.

What's next

  • Planned: play on Lichess or on your own board by voice through the Lichess Board API, using the same parser and matcher against the live game.
  • Non-voice inputs (switch access, eye tracking) plugged into the same move pipeline.
  • More real speakers in the test set, so the result is not one voice.
  • More languages, and a homophone list that learns from your corrections.
  • A WebGPU path for faster recognition.
